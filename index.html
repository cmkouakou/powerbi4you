1.2 Comment Power BI s'organise en entreprise Info

Avant d'ouvrir Power BI Desktop, une clarification qui évite un contresens fréquent chez les étudiants : on ne reçoit jamais un identifiant unique et on "commence à travailler" comme sur un tableur personnel. Dans une vraie entreprise, l'accès aux données est découpé en couches, chacune avec son propriétaire, sa raison d'être et son processus de création — le rôle powerbi_reader que tu utiliseras au sprint 1.6 n'est qu'une seule de ces couches. Notion — Qui crée un rôle, et pourquoi jamais "à la main" en production ?Gouvernance

Qui crée powerbi_reader (le rôle base de données) — un développeur backend ou un DBA, via un script SQL versionné dans le dépôt de code (une migration), jamais en tapant une commande directement sur la base de production. Raison : si le rôle doit être recréé (nouvel environnement, restauration après incident), le script garantit qu'il aura exactement les mêmes droits — ni plus, ni moins — sans dépendre de la mémoire de quelqu'un.

Qui crée un espace de travail et y assigne les rôles Viewer/Contributor/Member/Admin — un administrateur Power BI (souvent le "BI lead" ou l'équipe IT), généralement après une demande formelle ("j'ai besoin d'accès au dashboard Ventes") passant par un processus d'approbation, pas par un email direct entre collègues. Raison : chaque accès accordé doit pouvoir être justifié et retiré plus tard (départ d'un employé, changement de poste) — c'est ce qu'un auditeur vérifie lors d'un contrôle de conformité.

Pourquoi cette séparation stricte entre les 4 couches (et non un seul accès global) — parce qu'un même besoin change de couche selon la situation : donner à un analyste le droit de *publier* un rapport (couche espace de travail) ne doit jamais lui donner accès aux tables brutes de production (couche base de données) ; et donner à toute l'équipe Marketing le droit de *voir* le dashboard Ventes ne doit pas leur montrer les chiffres de chaque vendeur individuellement (couche RLS). Trois besoins différents, trois couches, trois responsables.

Le principe qui chapeaute tout ça s'appelle le principe du moindre privilège : chaque compte — humain ou technique — ne reçoit que les droits strictement nécessaires à sa tâche, jamais "au cas où". C'est exactement pourquoi powerbi_reader ne voit que 13 vues nettoyées du schéma reporting, et rien du schéma public où vivent les vraies tables applicatives.

1.3 Panorama des 13 vues disponibles Info

Le rôle powerbi_reader voit exactement 13 vues dans le schéma reporting, déjà nettoyées de toute donnée personnelle (voir migration 072_reporting_powerbi.sql). Chacune est soit une dimension (elle décrit un objet — un titre, un utilisateur, une date) soit une table de faits (elle enregistre un événement daté — un cours, une transaction).

Notion — Qu'est-ce qu'une "vue" (et pourquoi on en crée) ?SQL

Une vue (VIEW) est une requête SQL enregistrée sous un nom, que la base traite comme une table à chaque fois qu'on la lit. Elle ne stocke aucune donnée elle-même — elle recalcule le résultat à la volée à partir des vraies tables.

Pourquoi le schéma reporting passe par des vues plutôt que de connecter Power BI directement aux tables applicatives ? Trois raisons concrètes, toutes vérifiées sur ce projet :

1. Confidentialité — les vues excluent d'office les colonnes sensibles (email, notes libres, référence de paiement) et remplacent user_id par un hachage irréversible. Power BI ne voit jamais ce qu'une table brute contiendrait.

2. Stabilité — si la structure interne d'une table applicative change, on ajuste la vue une seule fois ; le modèle Power BI, lui, continue de voir les mêmes noms de colonnes.

3. Droits d'accès — le rôle powerbi_reader n'a de permission que sur le schéma reporting, jamais sur public où vivent les vraies tables. Une vue est donc aussi une frontière de sécurité.

1.5 Pourquoi ce schéma tient debout Info

Les 3 dimensions rayonnent vers les 4 tables de faits — c'est la forme "en étoile" qu'on construira formellement au sprint 4, mais autant voir la cible dès maintenant :

Notion — Le schéma en étoile : explication, utilité, contexteModélisation

Explication. Un schéma en étoile organise les données autour d'une table de faits centrale (les événements mesurables — un cours, une transaction, une analyse lancée) reliée à plusieurs tables de dimensions qui décrivent le contexte de ces événements (quel titre, quel utilisateur, quelle date). Vu de haut, ça dessine une étoile : les dimensions rayonnent depuis les faits.

Utilité. C'est la forme que DAX et le moteur de calcul de Power BI attendent pour être rapides et pour que les relations filtrent correctement d'une table à l'autre — filtrer sur une date dans v_dim_date doit automatiquement restreindre les cours dans v_quotes_history. Une seule grande table plate (tout mélangé) casse ce comportement et rend les mesures fausses ou lentes.

Contexte dans ce chantier. Nos 3 dimensions (v_dim_date, v_stocks, v_user_profiles) rayonnent vers 4 tables de faits couvrant marché, usage et revenus. Le sprint 4 formalise ces relations dans Power BI ; le sprint 4.7 précisera même qu'avec plusieurs faits partageant les mêmes dimensions, on parle plus justement de schéma en galaxie — une étoile qui s'est multipliée.

1.6 Premier chargement dans Power BI Desktop Pratique

Microsoft LearnGet data from relational data sources·Select a storage mode

Les identifiants du rôle powerbi_reader sont prêts à l'emploi — mais Power BI redemande quand même la chaîne de connexion complète à la première ouverture d'un nouveau rapport :

  1. Ouvre Power BI Desktop → onglet Accueil → Obtenir les données → cherche et choisis PostgreSQL database.
  2. Une boîte « Connect to data source » s'ouvre en premier (pas encore le Navigateur) :
    • Server : aws-0-eu-west-1.pooler.supabase.com:5432
    • Database : postgres
    • Connectivity mode : c'est ici, pas plus tard dans le Navigateur, que tu choisis Import — pas DirectQuery. Le pooler Supabase n'est pas dimensionné pour des requêtes répétées en direct depuis Power BI ; Import rapatrie les données une fois et les stocke dans le fichier .pbix.
  3. Toujours dans la même boîte, sous Connection credentials : Authentication kind = Basic, puis le Username/Password du rôle powerbi_reader. Clique OK — le Navigateur s'ouvre alors.
  4. Dans le Navigateur, déplie uniquement le schéma reporting (jamais public — le rôle n'y a de toute façon aucun accès). Il liste une quinzaine d'objets ; coche seulement les 7 vues listées en 1.4 (et elles seules, pour ce chantier).
  5. Clique sur Transform data (pas Load) — ça ouvre l'éditeur Power Query, où on travaillera aux sprints 2 et 3 avant de charger quoi que ce soit dans le modèle.
Pourquoi "Transform data" et pas "Load" ? Une fois chargées telles quelles, corriger un type de colonne ou renommer un champ oblige à tout retélécharger. Passer par Power Query d'abord permet de préparer les données une bonne fois, avant qu'elles n'entrent dans le modèle.
Le mode Import ne se choisit qu'une fois. Il est associé à la connexion, pas à chaque vue : tu ne le reverras plus après cette étape, même en ajoutant d'autres tables plus tard depuis la même source.
Dépannage — « too many connections for role powerbi_reader »Dépannage

Ce qui se passe — au clic sur Charger, Power BI ouvre plusieurs connexions en parallèle (jusqu'à 10 par défaut) pour charger les 7 vues en même temps. Le pooler Supabase limite le nombre de connexions simultanées autorisées pour le rôle powerbi_reader, et ce parallélisme le dépasse — d'où l'erreur PostgreSQL 53300.

Correctif immédiat — Fichier > Options et paramètres > Options > Fichier actuel > Chargement des données → dans la section « Parallel loading of tables », sélectionne le bouton radio « One (disable parallel loading) » (au lieu de « Default »). Clique OK. Ça force un chargement séquentiel des vues, une par une, au lieu d'un chargement en rafale. Relance ensuite Charger.

Si l'erreur persiste — ferme complètement Power BI Desktop (et tout autre client comme pgAdmin ou DBeaver connecté avec le même rôle) pour libérer les connexions restées ouvertes, patiente quelques secondes, puis rouvre et réessaie.

Si ça revient souvent même à 1 connexion — le rôle a probablement une limite de connexion basse côté PostgreSQL ; un administrateur peut l'augmenter depuis l'éditeur SQL Supabase : ALTER ROLE powerbi_reader CONNECTION LIMIT 10;

⚠️ Enregistrer ≠ Fermer et appliquer. Fermer et appliquer applique tes transformations au modèle en mémoire — ça n'écrit rien sur le disque. Le seul geste qui rend ton travail permanent, c'est Ctrl+S (ou Fichier > Enregistrer) sur le fichier .pbix. Un redémarrage forcé (mise à jour Windows, coupure) entre les deux efface tout le travail non enregistré, même si tu avais déjà cliqué sur "Fermer et appliquer".
Notion — Rendre son travail permanent et le reprendre sans tout refaireBonnes pratiques

Le réflexe à prendre — Ctrl+S après chaque étape importante de transformation (pas seulement en fin de sprint). Un projet Power BI long comme celui-ci mérite d'être sauvegardé aussi souvent qu'un document Word.

La récupération automatique existe, mais n'y compte pas — Power BI Desktop propose un filet de sécurité (Fichier > Options et paramètres > Options > Global > Récupération automatique), avec un intervalle réglable. Utile après un simple plantage logiciel, mais pas garanti après un arrêt brutal du système (redémarrage forcé, coupure électrique) — ce n'est pas un substitut à l'enregistrement manuel.

Garder des copies versionnées — à chaque jalon important (fin de sprint, avant une transformation risquée), enregistrer une copie datée du fichier (ex. chantier-brvm_sprint2_v1.pbix). Si un fichier se corrompt ou qu'une transformation casse tout, tu reviens à la dernière version saine au lieu de tout recommencer.

Éviter les redémarrages forcés pendant une session de travail — configurer les Heures d'activité de Windows (Paramètres > Windows Update > Heures d'activité) pour couvrir tes plages de travail habituelles. Windows évite alors de redémarrer automatiquement pendant ces heures-là.

2.1 Le principe : une recette, pas un bricolage Info

Microsoft LearnShape the initial data

Chaque action que tu fais dans l'éditeur Power Query — changer un type, renommer une colonne, filtrer une ligne — s'ajoute comme une étape dans le volet Étapes appliquées (repéré au sprint 1). Deux conséquences importantes :

  • Rien n'est destructif : tu peux revenir sur une étape, la modifier ou la supprimer sans tout recommencer.
  • L'ordre compte : chaque étape s'appuie sur le résultat de la précédente. On nettoie donc dans un ordre précis (2.6), pas au hasard.
Repère utile : à tout moment, clique sur une étape passée dans la liste pour voir l'état des données à ce stade précis — pratique pour comprendre ce qu'une étape a changé.

2.3 Valeurs nulles : ne pas nettoyer à l'aveugle Pratique

Microsoft LearnSimplify the data structure

Sur ce jeu de données, un null n'est pas toujours une erreur — c'est parfois l'information elle-même. Deux cas très différents à traiter différemment :

  • pseudo_user_key nul (dans v_user_profiles, v_abonnements, v_analyses_quota_daily) : l'événement n'est rattaché à aucun utilisateur identifié (action système, session anonyme). Selon ce que la page doit montrer, tu filtres ces lignes ou tu les gardes sous un segment "Non attribué" — mais tu ne les supprimes jamais sans le décider explicitement.
  • Colonnes bancaires nulles dans v_fundamentals (pnb_xof, rbe_xof, credit_xof, depot_xof, marge_interets_xof…) : ces ratios n'existent que pour les banques. Un null ici sur une société commerciale (ex. Sonatel, Orange CI) n'est pas une donnée manquante — c'est normal, la colonne ne s'applique pas.
Piège à éviter : remplacer ces nulls bancaires par 0 "pour que ça calcule" fausserait toute moyenne ou tout total sur ces colonnes (une société non-bancaire apparaîtrait avec un PNB de 0 FCFA au lieu de "non applicable"). Laisse le null tel quel — DAX l'ignore correctement dans AVERAGE/SUM ; c'est seulement dans les visuels qu'on choisira d'exclure les non-banques (sprint 6).

Un vrai nettoyage de nulls reste utile dans un cas : une ligne entièrement vide ou une clé de jointure absente (ex. ticker nul dans v_quotes_history, qui rendrait la ligne inutilisable). Là, Accueil → Réduire les lignes → Supprimer les lignes → Supprimer les lignes vides, ou un clic droit sur l'en-tête de colonne → Supprimer les lignes vides ciblé sur la colonne clé.

2.8 Vérifier que le query folding tient Pratique

Microsoft LearnFix performance issues

Le query folding est le mécanisme par lequel Power Query traduit tes étapes en SQL et les fait exécuter par Supabase plutôt que par Power BI. Tu ne l'actives pas — il est automatique — mais tes choix déterminent jusqu'où il se propage.

Comment vérifier : volet Étapes appliquées → clic droit sur une étape → cherche Afficher la requête native.

  • En gras → le folding fonctionne, clique pour voir le SQL envoyé à Supabase
  • Grisé → le folding est cassé à cette étape ; remonte les étapes une à une jusqu'à en trouver une où l'option redevient active, c'est là que ça a lâché
Les trois briseurs — moyen mnémotechnique « I-F-T » : colonne d'Index, Fusion entre deux sources différentes, changement de Type de données. Si le SQL ne sait pas l'exprimer, le folding s'arrête — et il ne reprend jamais : toutes les étapes suivantes se feront localement, même celles qui auraient pu être traduites.

La conséquence directe pour ce chantier : la section 2.2 te fait changer des types de données. C'est le briseur n° 3. Deux façons d'en limiter l'impact :

  1. Corriger à la source quand c'est possible. Un montant stocké en texte se règle mieux dans la vue SQL (cast(colonne as numeric)) que dans Power Query — le folding reste intact et Power BI reçoit le bon type d'emblée.
  2. Ordonner les étapes. Filtres et suppressions de colonnes d'abord (elles foldent et réduisent le volume transféré), changements de type et colonnes d'index en dernier. C'est déjà la logique de 2.6 — voici maintenant la raison technique derrière.
Exercice de démonstration. Sur une requête dupliquée : ajoute un filtre de date, vérifie que la requête native s'affiche et contient bien ton WHERE. Ajoute ensuite une colonne d'index, puis reclique droit : l'option est grisée. Déplace l'étape d'index avant le filtre par glisser-déposer et observe que le folding ne survit plus du tout. Même résultat à l'écran, performance très différente.

3.8 Dépivoter et pivoter : changer la forme d'une table Pratique

Microsoft LearnShape the initial data

Deux transformations symétriques, et une notion que le PL-300 teste systématiquement :

  • Dépivoter (unpivot) : colonnes → lignes. Transforme une table large en table haute. Produit toujours deux colonnes nommées Attribut (les anciens en-têtes) et Valeur (le contenu des cellules).
  • Pivoter : lignes → colonnes, avec une fonction d'agrégation (Somme, Moyenne, Compte, Min, Max, Médiane).

Le cas classique : un fichier Excel avec une colonne « 2024 », une colonne « 2025 », une colonne « 2026 ». Lisible pour un humain, inexploitable en DAX — impossible de totaliser les trois années sans écrire une formule par colonne. Dépivoter donne une colonne Année et une colonne Montant, et tout redevient simple.

Ce que ça t'apprend sur ton propre travail. Aucune de tes 7 vues n'a besoin d'être dépivotée — elles sortent déjà en format haut et étroit. Ce n'est pas un hasard : une base relationnelle produit nativement la forme que DAX attend. Le problème du dépivotage est un problème d'Excel, où les humains étalent les données pour les lire. Retenir ça, c'est comprendre pourquoi le travail fait côté SQL t'a épargné une étape entière.

Exercice en bac à sable — aller-retour, pour voir les deux sens :

  1. Duplique v_quotes_history, garde seulement date, ticker, close
  2. Filtre sur 3 ou 4 tickers pour garder l'aperçu lisible
  3. Sélectionne ticker → onglet Transformer → Colonne dynamique → colonne de valeurs = close, fonction d'agrégation = Moyenne
  4. Tu obtiens une colonne par ticker : c'est la forme « Excel ». Regarde à quel point elle est agréable à lire et pénible à exploiter
  5. Sélectionne ces colonnes de tickers → Transformer → Dépivoter les colonnes — tu retrouves la forme d'origine, avec Attribut et Valeur à renommer
  6. Désactive le chargement de la requête
Note performance. Ces deux transformations cassent souvent le query folding (2.8) : le SQL n'a pas d'équivalent direct du pivot dynamique. Une raison de plus de les placer en fin de séquence, après les filtres.

La variante qui sauve du temps : Dépivoter les autres colonnes. Le menu offre trois options, et le choix entre elles change la robustesse de ta requête :

OptionCe qu'elle dépivoteQuand la choisir

L'autre option aurait ignoré la nouvelle colonne en silence.

3.11 Niveaux de confidentialité : quand Power BI refuse de croiser deux sources Concept

Microsoft LearnExercise - Load data in Power BI Desktop

Au moment de fusionner deux requêtes issues de sources différentes, une fenêtre Niveaux de confidentialité peut s'ouvrir et demander de classer chaque source.

NiveauCe qu'il autorise
PublicDonnées librement partageables avec les autres sources

PrivateJamais partagé avec aucune autre source
Ce que le réglage signifie vraiment. Il ne dit pas qui a le droit de voir les données — il dit si le moteur Power Query peut faire transiter les valeurs d'une source vers une autre pendant l'exécution. Marquer une source Private ne protège pas les données d'un lecteur du rapport; ça empêche simplement Power Query de les envoyer à l'autre système pour effectuer la jointure.

Le piège de performance. Quand deux sources ont des niveaux incompatibles, Power Query refuse de déléguer la jointure et rapatrie tout localement — le query folding (2.8) tombe. 4.4 Cardinalité et sens de filtrage : pourquoi "Unique" Info

Pour chaque relation, laisse le sens de filtrage croisé sur Unique (la dimension filtre la table de faits) plutôt que Les deux (bidirectionnel). Ici, deux dimensions (v_user_profiles, v_dim_date) touchent plusieurs tables de faits à la fois : en bidirectionnel, un filtre posé sur une page "Revenus" pourrait se propager en silence jusqu'à des visuels de la page "Utilisateurs", et inversement — des chiffres qui bougent sans qu'on comprenne pourquoi. En sens unique, chaque filtre reste prévisible.

Règle simple pour débuter : Unique par défaut, toujours. Tu passeras en bidirectionnel plus tard, ponctuellement, seulement si un besoin précis l'exige et que tu comprends pourquoi.

4.5 Cas particulier : deux relations vers la même dimension Info

v_abonnements a deux colonnes de date (date_debut, date_fin) qui pourraient toutes les deux se relier à v_dim_date. Power BI n'autorise qu'une seule relation active à la fois entre deux tables — la seconde se crée automatiquement en pointillé, inactive :

Laisse date_debut active (elle répond à "combien de nouveaux abonnements par jour"). La relation inactive sur date_fin reste disponible pour plus tard : on l'activera ponctuellement dans une mesure avec USERELATIONSHIP() le jour où tu voudras analyser les résiliations par date de fin (hors périmètre de ce chantier, mais bon à savoir que c'est possible sans dupliquer la table).

4.6 Pourquoi v_fundamentals ne se relie pas à v_dim_date Info

v_fundamentals est annuelle (fiscal_year est un entier comme 2025, pas une date calendaire précise). La relier à un calendrier journalier n'aurait pas de sens — fiscal_year reste un simple champ de filtre/segment autonome dans les visuels de la page Marché, sans relation dédiée.

4.7 Une précision de vocabulaire : étoile ou galaxie ? Info

Au sprint 1, on a appelé ce montage "schéma en étoile" pour simplifier. Maintenant que le modèle est sous tes yeux : un schéma en étoile au sens strict n'a qu'une seule table de faits entourée de ses dimensions. Ici, on a quatre tables de faits (v_quotes_history, v_fundamentals, v_analyses_quota_daily, v_abonnements) qui partagent des dimensions communes (v_dim_date, v_stocks, v_user_profiles) sans jamais se relier entre elles directement. Le terme exact est schéma en galaxie (ou "constellation de faits") — le principe de fond (dimensions séparées des faits) reste identique, seul le nom change selon le nombre de tables de faits.

4.10 Tes trois premières mesures Pratique

Notion — DAX, c'est quoi au juste ?DAX

DAX (Data Analysis eXpressions) est le langage de formules de Power BI — le même esprit qu'une formule Excel, mais conçu pour raisonner sur des tables entières plutôt que sur des cellules isolées.

Utilité. DAX sert à créer deux choses : des colonnes calculées (vues au sprint 3 — une valeur ajoutée à chaque ligne d'une table, figée au chargement) et des mesures (ci-dessous — un calcul qui se refait à la volée selon ce que l'utilisateur regarde). La quasi totalité du travail DAX porte sur les mesures, car ce sont elles qui rendent un dashboard interactif.

Contexte. Le mot-clé le plus important de DAX est CALCULATE : il permet de changer le contexte de filtre d'un calcul (par exemple, comparer le volume du titre sélectionné contre celui de tout le marché, dans la même visualisation). Le sprint 5 lui est entièrement consacré.

Clic droit sur _Mesures → Nouvelle mesure :

Nombre de titres actifs = CALCULATE(
    DISTINCTCOUNT(v_stocks[ticker]),
    v_stocks[is_active] = TRUE()
)

Volume total = SUM(v_quotes_history[volume])

Total abonnements (FCFA) = SUM(v_abonnements[montant])

Différence à retenir avec une colonne calculée (sprint 3) : une mesure ne se calcule pas ligne par ligne au chargement, elle se recalcule à la volée selon le contexte de filtre du visuel qui l'affiche (le titre sélectionné, la période du segment…). C'est ce qui la rend réutilisable partout dans le dashboard sans jamais dupliquer de donnée.

Sprint 5

DAX avancé

Objectif : écrire des mesures qui comparent des périodes entre elles (année sur année, cumul depuis le début de l'année), et des ratios sûrs qui ne cassent jamais sur une division par zéro. C'est le sprint où DAX cesse d'être décoratif et devient réellement utile.

5.1 Ce que change CALCULATE Info

Toutes les mesures du sprint 4 (Volume total, Nombre de titres actifs…) héritent silencieusement du contexte de filtre posé par le visuel qui les affiche : un tableau par titre les recalcule ticker par ticker, un segment de date les recalcule période par période. CALCULATE est la seule fonction DAX qui peut modifier ce contexte plutôt que le subir — c'est elle qui rend possible tout ce qui suit : comparer une période à une autre exige de désobéir, dans un coin de la formule, au filtre que le visuel a posé.

5.2 Time intelligence : cumul depuis le début de l'année Pratique

Ces fonctions exigent que v_dim_date soit marquée comme table de dates (fait au sprint 4) — sans ça, elles renvoient une erreur ou un résultat silencieusement faux.

Volume YTD =
CALCULATE(
    [Volume total],
    DATESYTD(v_dim_date[date_jour])
)

Posée dans un visuel par mois, cette mesure ne montre pas le volume du mois seul, mais le cumul depuis le 1er janvier jusqu'à ce mois — DATESYTD remplace le filtre de date du visuel par la plage "du 1er janvier de l'année en cours jusqu'à la date affichée".

5.3 Comparer une année à l'autre Pratique

Volume N-1 (même période) =
CALCULATE(
    [Volume total],
    SAMEPERIODLASTYEAR(v_dim_date[date_jour])
)

Évolution volume vs N-1 (%) =
DIVIDE(
    [Volume total] - [Volume N-1 (même période)],
    [Volume N-1 (même période)]
)
Pourquoi DIVIDE et pas l'opérateur / — si le titre n'avait aucune transaction l'année précédente, [Volume N-1] vaut 0 ou vide, et / renverrait une erreur qui casserait tout le visuel. DIVIDE(numérateur, dénominateur) renvoie un blanc proprement dans ce cas — troisième argument optionnel pour une valeur de repli si tu en veux une précise (ex. 0).

5.4 Cumul glissant (running total) Pratique

Même principe que le YTD, mais sans repartir de zéro chaque 1er janvier — utile pour v_abonnements où on veut voir le total encaissé progresser sans jamais redescendre :

Cumul abonnements (FCFA) =
CALCULATE(
    [Total abonnements (FCFA)],
    FILTER(
        ALLSELECTED(v_dim_date),
        v_dim_date[date_jour] <= MAX(v_dim_date[date_jour])
    )
)

ALLSELECTED(v_dim_date) retire temporairement le filtre de date posé par le visuel (sans toucher aux autres filtres, par ex. un segment sur le plan tarifaire), puis FILTER ne garde que les dates antérieures ou égales à la date de la ligne courante — chaque ligne du visuel additionne donc tout ce qui la précède.

5.5 Un ratio bancaire, proprement Pratique

v_fundamentals contient credit_xof et depot_xof, nuls pour les sociétés non bancaires (sprint 2). Une mesure de ratio doit rester silencieuse sur ces lignes plutôt que d'afficher une erreur :

Ratio Crédits/Dépôts =
DIVIDE(
    SUM(v_fundamentals[credit_xof]),
    SUM(v_fundamentals[depot_xof])
)

Posée dans un tableau mêlant banques et non-banques, cette mesure affiche un ratio pour les premières et une cellule vide pour les secondes — exactement le comportement voulu, sans IF ni test de nullité écrit à la main.

5.6 Mettre le pourcentage en forme correctement Pratique

DAX ne fait pas la distinction entre "0,145" et "14,5 %" — c'est un nombre décimal, point. Une fois la mesure Évolution volume vs N-1 (%) créée :

  1. Sélectionne la mesure dans le volet Données
  2. Onglet contextuel Outils de mesure → format %, 1 décimale
Piège à éviter : ne jamais multiplier la formule par 100 pour "faire apparaître" le pourcentage — la valeur stockée doit rester le ratio brut (0,145), seule sa mise en forme d'affichage change. Multiplier par 100 fausserait tout calcul ultérieur qui réutilise cette mesure (moyenne, écart, tri).

7.5 Vérifier la performance avant de livrer Pratique

Microsoft LearnFix performance issues

Affichage → Analyseur de performances → Actualiser les visuels : chaque visuel affiche son temps de calcul DAX et de rendu. Si c'est l'actualisation qui traîne, le problème est en amont et l'outil est ailleurs : dans l'éditeur Power Query, onglet Outils → Démarrer les diagnostics, tu rejoues tes transformations, puis Arrêter les diagnostics.
